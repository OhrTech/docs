Your organisation's own apps, the ones you build, reach devices through OhrTech: you upload each
build as a version of the app, choose which version the devices must run, and the devices install
it, with no store and no one at the device.

## Apps, versions and fleets

- An **app** is a package name, such as `com.example.kiosk`, your name for it, and an id, such as
  `app_44n36syg958kyv8gzmq6f59tkq`, that never changes. Several apps may share a package: flavours of one app
  built for different fleets, each with its own id and versions.
- Each **version** is one APK you uploaded. The API reads its version code, version name, signer and
  permissions from the APK itself.
- An app goes to the devices of the **fleets** you assign it to: the devices directly in each fleet,
  not those of the fleets below it. A device holds one app per package, so a fleet gets at most one
  of the apps that share a package (409 "Package already in this fleet"). A device that leaves the
  fleet, or a fleet you take the app from, uninstalls it.

Each version is in one of three states:

| State | Devices |
|---|---|
| `held` | Never download it, never install it. Every upload starts here unless you say otherwise. |
| `available` | Download it ahead, over Wi-Fi or Ethernet only, and keep it: your app installs it when it is ready, through the [Device SDK](/device-sdk/). |
| `enforced` | Install it: every device in the app's fleets runs the newest enforced version, at the time its fleet chooses (see [when devices install](#when-devices-install)). |

Devices only ever move up: one that already runs a newer version than the enforced one keeps it.

Besides your own apps (`kind`: `org`), `GET /v1/apps` lists OhrTech's:

- **catalog** apps, such as the Vanadium browser: assign them to your fleets like your own.
- **platform** apps, such as Vanadium System WebView: part of the OS on every device, updated
  wherever the OS has them. You don't assign them, and devices never uninstall them.

OhrTech releases the versions of both. Each of your fleets chooses whether it gets them
[automatically or only once you approve one](#ohrtechs-apps-automatic-or-manual).

## Add an app

Once per app. Needs `ManageApps`.

<Tabs syncKey="lang">
<TabItem label="C#">

```csharp
var app = await api.CreateAppAsync(new CreateAppRequest { PackageName = "com.example.kiosk", Name = "Kiosk" });
await api.AddFleetAppAsync("flt_2dn47a2xa58j1txv8m28spkmyb", app.AppId); // install it on that fleet's devices
```

</TabItem>
<TabItem label="ohr">

```sh
ohr apps create com.example.kiosk --name Kiosk    # shows the new app's id
ohr apps assign app_44n36syg958kyv8gzmq6f59tkq flt_2dn47a2xa58j1txv8m28spkmyb
```

</TabItem>
<TabItem label="curl">

```sh
curl https://api.ohrtech.net/v1/apps \
  -H "Authorization: Bearer $OHR_TOKEN" -H "Content-Type: application/json" \
  -d '{"packageName": "com.example.kiosk", "name": "Kiosk"}'
curl -X PUT https://api.ohrtech.net/v1/fleets/flt_2dn47a2xa58j1txv8m28spkmyb/apps/app_44n36syg958kyv8gzmq6f59tkq -H "Authorization: Bearer $OHR_TOKEN"
```

</TabItem>
</Tabs>

If you belong to several organisations, pass `orgId`, the organisation to add it to. For a
flavour, add another app with the same package and its own name, and assign it to its own fleets.

## Upload a version

The request body is the APK itself: one signed `.apk`, up to 1 GiB, not an `.aab`. Name the app by
its id in the path: the API refuses an APK of any other package (400, "Wrong app"), so a build pipeline that
picks up the wrong file can't release the wrong app.

<Tabs syncKey="lang">
<TabItem label="C#">

```csharp
var version = await api.UploadApkAsync("app_44n36syg958kyv8gzmq6f59tkq", "app-release.apk", state: "enforced");
Console.WriteLine($"{version.PackageName} {version.VersionName} ({version.VersionCode}) is {version.State}");
```

</TabItem>
<TabItem label="ohr">

```sh
ohr apps upload app_44n36syg958kyv8gzmq6f59tkq app-release.apk --enforce
```

</TabItem>
<TabItem label="curl">

```sh
curl "https://api.ohrtech.net/v1/apps/app_44n36syg958kyv8gzmq6f59tkq/versions?state=enforced" \
  -H "Authorization: Bearer $OHR_TOKEN" -H "Content-Type: application/octet-stream" \
  --data-binary @app-release.apk
```

</TabItem>
</Tabs>

The API checks the APK before it keeps it:

| Answer | When |
|---|---|
| 201 | The new version, as `AppVersionDto` |
| 400 "Not an installable APK" | Not an APK, or not signed with APK signature scheme v2 or later |
| 400 "Wrong app" | The APK is another package than the app in the path |
| 409 "Not a newer version" | Its version code isn't higher than every version already uploaded |
| 409 "Different signing key" | It is signed with another key than the previous version, so devices would refuse it as an update |

A 409 also carries `appId`, `packageName` and `versionCode`. "Not a newer version" adds
`latestVersionCode` and `exists`, which is `true` when this very version code is already uploaded:
a pipeline that runs again can treat that as done. "Different signing key" adds
`signingKeySha256` and `expectedSigningKeySha256`. If you rotated the key with APK signature scheme
v3, upload with `allowNewSigningKey=true`.

## Follow the rollout

`GET /v1/apps/{appId}/rollout` shows, for every device the app applies to, the version it runs, the
version it should run (`targetVersionCode`), and where it is: `up_to_date`; `held` (a manual fleet
hasn't approved the newest version); `pending` (it hasn't started); `waiting` (it has the version and
waits for its fleet's update timing, such as the screen to be off); `installing`; or `failed`, with
the device's reason in `detail`.

<Tabs syncKey="lang">
<TabItem label="C#">

```csharp
var rollout = await api.WaitForRolloutAsync("app_44n36syg958kyv8gzmq6f59tkq", TimeSpan.FromMinutes(15));
foreach (var d in rollout.Devices.Where(d => d.Status == "failed"))
    Console.WriteLine($"{d.DeviceId}: {d.Detail}");
```

`WaitForRolloutAsync` returns once every online device is up to date, held, waiting for its fleet's
timing, or failed; pass `untilInstalled: true` to wait for the timed installs too. Offline devices
install the version when they next connect.

</TabItem>
<TabItem label="ohr">

```sh
ohr apps rollout app_44n36syg958kyv8gzmq6f59tkq --wait
```

</TabItem>
</Tabs>

To release from a build pipeline, see [release from CI](/management-api/recipes/release-from-ci/).

## When devices install

Installing an update closes the app being updated, and a WebView update closes every app that is
showing web content at that moment (anything typed into a web page and not yet saved is lost). So
each fleet chooses when its devices install enforced versions; they download them whenever they can.

| `mode` | Devices install |
|---|---|
| `screen_off` | Once nobody has used the device for 2 minutes and no call is active. The default. A device that is never idle waits. |
| `window` | Only in the window, the device's local time (`days` 1 = Monday to 7, `start`, `end`), even if someone is using the device. |
| `window_or_screen_off` | Either. |
| `immediate` | At once, even mid-use. |

Only updates wait: an app a device doesn't have yet (just added to the fleet, or a device that just
joined it) installs at once, since it can't close anything. If a waiting update is no longer wanted
(the app leaves the fleet, the device moves, or the version is held), the device drops it without
installing.

A fleet without its own timing follows its parent's. Operating system updates have their own settings.

<Tabs syncKey="lang">
<TabItem label="C#">

```csharp
await api.SetUpdateTimingAsync("flt_2dn47a2xa58j1txv8m28spkmyb", new UpdateTimingRequest
{
    Mode = "window", Start = "02:00", End = "05:00", Days = [1, 2, 3, 4, 5],
});
```

</TabItem>
<TabItem label="ohr">

```sh
ohr fleets timing flt_2dn47a2xa58j1txv8m28spkmyb --window 02:00-05:00 --days mon,tue,wed,thu,fri
```

</TabItem>
</Tabs>

## OhrTech's apps: automatic or manual

For each catalog and platform app, a fleet's policy is:

- **automatic** (the default): each version OhrTech releases installs at the fleet's timing.
- **manual**: the fleet's devices stay on the version you approved, for as long as you choose.
  Nothing changes until someone in your organisation approves a newer one. OhrTech can't override
  it.

`GET /v1/fleets/{fleetId}/apps/{appId}/policy` shows the policy, the version the fleet gets, and
the newer versions that wait for approval, with OhrTech's notes and whether each fixes security
vulnerabilities. Waiting matters most for the WebView: it shows web content inside apps, and an
outdated one has publicly known vulnerabilities that any web page an app opens, including an ad or
a link, can use. A manual fleet's organisation gets an email when a version waits, and weekly while
a security update waits (`reminders`).

<Tabs syncKey="lang">
<TabItem label="C#">

```csharp
// Stay on what the fleet runs now:
var policy = await api.SetFleetAppPolicyAsync("flt_2dn47a2xa58j1txv8m28spkmyb", "app_3k7fx2qd0m9b4tz1s8c6ve5hwy", new SetAppPolicyRequest { Mode = "manual" });
// Later, approve the newest waiting version:
policy = await api.SetFleetAppPolicyAsync("flt_2dn47a2xa58j1txv8m28spkmyb", "app_3k7fx2qd0m9b4tz1s8c6ve5hwy",
    new SetAppPolicyRequest { Mode = "manual", ApprovedVersionCode = policy.Waiting[0].VersionCode });
```

</TabItem>
<TabItem label="ohr">

```sh
ohr apps policy app_3k7fx2qd0m9b4tz1s8c6ve5hwy flt_2dn47a2xa58j1txv8m28spkmyb --manual
ohr apps approve app_3k7fx2qd0m9b4tz1s8c6ve5hwy flt_2dn47a2xa58j1txv8m28spkmyb
```

</TabItem>
</Tabs>

To try a version on a few devices first, move them to a small child fleet and approve it there.
An OS update brings its own WebView: a fleet's devices keep a newer one that came with the OS.

**microG** is in the catalog as two apps: microG Services and microG Companion. They stand in for
Google Play services and the Play Store, so apps written against Google's libraries get push
messages (Firebase Cloud Messaging), Google sign-in and Google's location API. Add both to a fleet
like any catalog app. They run as ordinary apps in Android's app sandbox, and location comes from
the device's own location service.

## What your apps may do on a device

The apps the hub installs get Android permissions in three ways:

- **Permissions a person would be asked about** (location, camera, SMS, ...) and **special access**
  (draw over other apps, usage access, ...) are granted automatically, as soon as the app is
  installed. The person at the device can't revoke them: your fleet's devices are managed.
- **Battery optimization:** an app that declares `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is exempted,
  so Doze doesn't hold it back.
- **Privileged permissions**, which Android gives only to apps built into the OS, are granted once
  OhrTech approves them for your organisation. Then every app of yours that requests one gets it.
  Ask OhrTech for the ones your apps need. Until then an app runs without them, as Android runs any
  app without a permission it wasn't granted.

A privileged permission goes only to the app signed with the key the hub knows it by: another APK
under the same package name gets nothing. If an approval is withdrawn, devices revoke the permission
at their next check-in and restart the app. A few privileged permissions are never granted, because
they would let an app take over the device or escape management (granting itself permissions,
changing secure settings, installing packages, managing users).

`GET /v1/apps/{appId}/permissions` lists the privileged permissions an app's versions request and,
for each, `granted`, `waiting` (not approved) or `never`:

```http
GET /v1/apps/app_44n36syg958kyv8gzmq6f59tkq/permissions

[
  { "permission": "android.permission.CHANGE_DEVICE_IDLE_TEMP_WHITELIST", "state": "granted",
    "approvedFor": "org", "versionCodes": [241, 240], "note": "Push: wake the app for incoming calls" },
  { "permission": "android.permission.WRITE_SECURE_SETTINGS", "state": "never",
    "approvedFor": null, "versionCodes": [241], "note": null }
]
```

`GET /v1/orgs/{orgId}/permission-approvals` lists what OhrTech approved for your organisation.

## Permissions

`ManageApps` adds apps, uploads versions, changes their state and assigns them to fleets. Every
member of an organisation holds it; grant it to the service account your pipeline uses. Seeing
apps, versions and rollouts needs `ManageApps` or `ViewDevices`.

A service account limited to some fleets can upload held versions, but can offer or enforce a
version only when every fleet with the app is within its limits.

A fleet's update timing and its policies for OhrTech's apps need `ManageApps` in the fleet's
organisation. Catalog and platform versions are released by OhrTech (403 "Managed by OhrTech").
