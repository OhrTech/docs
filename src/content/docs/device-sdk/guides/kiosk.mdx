import { Tabs, TabItem } from '@astrojs/starlight/components';

In kiosk mode the device runs one app and nothing else. The OhrTech Agent pins the app with
Android's lock task mode, as the system: the person at the device can't leave the app, and the app
can't unpin itself through Android either. Only the OhrTech Agent ends kiosk mode, when your app
asks and the fleet allows it, when the hub lifts it, or when staff type the exit PIN.

There are two ways in:

- **From your app**, with `OhrKiosk.start`. Needs the fleet's `kiosk` grant.
- **From the fleet**, with the **Kiosk app** setting. The device starts and pins the app at every
  boot. Your app needs no SDK call and no grant.

Either way, the [watchdog](#the-watchdog) brings the app back when it crashes, hangs or leaves, and
the [exit PIN](#the-exit-pin) lets staff leave kiosk mode for a while.

`start`, `stop` and `state` need OhrTech Agent 1059 or later. The watchdog, the exit PIN, the Kiosk
app setting, `requestExit` and `heartbeat` need Agent 1061 or later. On an older Agent, `requestExit`
and `heartbeat` throw `Unsupported` with `needsAgent` 1061 (in TypeScript, `heartbeat` has no
effect instead). [Response timeouts](#response-timeouts)
and the watchdog's pause while the screen is off need Agent 1062 or later.

In Kotlin and Java, `start`, `stop`, `state` and `requestExit` are blocking calls into the Agent:
make them off the main thread. In Dart, TypeScript and C# they are asynchronous.

`start` pins the activity's task and returns once Android has locked it, so `state()` right after
says so. The task must be one of your app's own (`InvalidConfig` with `field` `taskId` otherwise).

Kiosk mode your app started lasts until it ends or the device restarts. After a restart, call
`start` again when your app starts: an app that pins itself is not pinned again by the device. To
have the device do it at every boot, use the fleet's [Kiosk app](#kiosk-mode-from-the-fleet)
setting instead.

### What stays available

The second parameter of `start` (in Dart the named parameter `features`) says what the person at
the device may still use. Combine the values with `or` in Kotlin and `|` elsewhere. The default is
the power menu and the status bar's information (`GLOBAL_ACTIONS` and `SYSTEM_INFO`).

| Kotlin, Java: `OhrKiosk.Feature`; TypeScript: `OhrKioskFeature` | Dart: `OhrKioskFeature` | C#: `OhrKioskFeatures` | Allows |
|---|---|---|---|
| `SYSTEM_INFO` | `systemInfo` | `SystemInfo` | The status bar's information: clock, battery, signal |
| `NOTIFICATIONS` | `notifications` | `Notifications` | Notifications and the notification shade |
| `HOME` | `home` | `Home` | The Home button |
| `OVERVIEW` | `overview` | `Overview` | The Overview (recent apps) button |
| `GLOBAL_ACTIONS` | `globalActions` | `GlobalActions` | The power menu (a long press of the power button) |
| `KEYGUARD` | `keyguard` | `Keyguard` | The lock screen |
| `BLOCK_ACTIVITY_START_IN_TASK` | `blockActivityStartInTask` | `BlockActivityStartInTask` | Blocks activities of apps other than yours from starting in the pinned task |

These are Android's lock task features (`DevicePolicyManager.LOCK_TASK_FEATURE_*`), with the same
values. When the exit PIN's power menu item is on, the device keeps the power menu available
whatever you pass, since the item is in it.

### State and stop

`state()` (`GetStateAsync()` in C#) returns:

| Field | |
|---|---|
| `pinned` | Your app is the one in kiosk mode now |
| `mode` | The device's lock task mode: `none`, `locked` (kiosk mode) or `pinned` (Android's screen pinning) |
| `features` | The features kiosk mode was started with |
| `appMayExit` | The fleet lets kiosk apps leave kiosk mode themselves |

`stop()` ends kiosk mode when your app is the one pinned and the fleet's **Kiosk apps may leave
kiosk mode** setting (`kiosk.app_exit`) is on, which it is by default. When the fleet turns it off,
`stop()` throws `NotAllowed("kiosk")`: only the hub or the exit PIN end kiosk mode then. When
another app, or no app, is pinned, `stop()` does nothing.

<Tabs syncKey="lang">

```kotlin
withContext(Dispatchers.IO) {
    val state = OhrKiosk.state()
    if (state.pinned && state.appMayExit) OhrKiosk.stop()
}
```

</TabItem>
<TabItem label="Java">


</TabItem>


</TabItem>

When the fleet made your app its kiosk app, `stop()` is an exit for a while, as with the exit PIN,
except that your app stays in front: the device pins it again after the fleet's exit time
(`kiosk.exit_minutes`, 10 minutes by default), when the screen turns off, or when your app's process
starts again, whichever comes first. A notification counts down, with **Back to kiosk** to end it
early. When your app pinned itself with `start`, `stop()` simply ends kiosk mode.

The device's `mode` each time kiosk mode starts or ends comes from `OhrKiosk.modeChanges` (a Kotlin
`Flow`, a Dart stream), `listenMode(executor, listener)` in Java, `addModeListener(listener)` in
TypeScript, and the `ModeChanged` event or `ModeChanges(ct)` in C#. Call `state()` to learn whether
it is your app's.

## Kiosk mode from the fleet

Set these in the fleet's settings in the portal (category **Kiosk**; the response timeout is under
**Apps**), or per device with the [Management API](/management-api/guides/settings/).

| Key | Label | Value | Default |
|---|---|---|---|
| `kiosk.app` | Kiosk app | The package to run in kiosk mode; `"default"` for none | `"default"` |
| `kiosk.watchdog` | Kiosk app watchdog | `true` or `false` | `true` |
| `kiosk.exit_pin` | Kiosk exit PIN | `{"code": "2468"}`: 4 to 12 digits | not set |
| `kiosk.exit_minutes` | Kiosk exit time | `"5"`, `"10"`, `"15"`, `"30"` or `"60"` (minutes) | `"10"` |
| `kiosk.exit_triggers` | Ways to open the exit PIN | Any of `power_menu`, `keys`, `gesture`, `app` | all four |
| `kiosk.exit_keys` | Exit key sequence | `volume_down_5` or `volume_both_hold` | `volume_down_5` |
| `kiosk.exit_corner` | Exit taps corner | `top_left`, `top_right`, `bottom_left`, `bottom_right` | `top_left` |
| `kiosk.app_exit` | Kiosk apps may leave kiosk mode | `true` or `false` | `true` |
| `apps.response_timeout` | Response timeouts | Per app, `{"app_…": seconds}`: 1 to 2147483 each. See [response timeouts](#response-timeouts) | not set |

With **Kiosk app** set, the device starts that app and pins it at every boot, with the power menu
and the status bar's information available. If the app isn't installed yet, the setting waits and
applies once it is. Setting it back to `"default"` ends the kiosk mode the fleet started. An app
that pinned itself with the SDK keeps its kiosk mode: the fleet's kiosk app doesn't take over from it.

## The watchdog

When the app in kiosk mode crashes, stops responding or leaves the screen, the OhrTech Agent
starts it again and pins it again. This works for an app the fleet set as **Kiosk app** and for an
app that pinned itself with `start`. It is on unless the fleet turns **Kiosk app watchdog** off.

- **Crashes and exits.** When kiosk mode ends without the app, the hub or the exit PIN ending it,
  the Agent brings the app back: at once the first time, then after 5 seconds, then 30 seconds,
  then 2 minutes.
- **Hangs.** When Android reports that the app isn't responding (an ANR), the Agent stops the app
  and so starts it again, without waiting for anyone to answer Android's dialog. How long the app
  may stay busy before Android says so is 5 seconds, or the fleet's
  [response timeout](#response-timeouts) for it.
- **A hung UI thread that Android doesn't notice.** Call `heartbeat()`: see below.
- **The screen off.** With Agent 1062 or later, hang detection, heartbeat and ANR alike, pauses
  while the screen is off: an app may sleep with the screen, its timers and frames stopped. When
  the screen comes back on, the app gets a full timeout again before a missing heartbeat counts.
  An ANR Android declared while the screen was off counts only if it outlasts a full timeout after
  the screen came on: the fleet's response timeout for the app, or Android's 5 seconds.
- **Giving up.** When the app stops for the 5th time within 10 minutes, the Agent stops trying and
  shows that the app isn't working, with a **Try again** button.

A new version of your app being installed doesn't count as a crash: the app is started again
2 seconds later. While the Agent waits to start the app, a cover over the whole screen keeps the
device from being used outside it. The device reports each restart, and each time it gives up, to
the hub.

With the watchdog off, kiosk mode ends when the app leaves. The device stays out of kiosk mode
until your app calls `start` again or, for the fleet's kiosk app, until the device restarts or the
fleet's kiosk settings change.

### Heartbeat

A UI thread stuck in a loop, or waiting on a lock, doesn't always cause an ANR: Android reports one
only when input or a broadcast goes unanswered. `heartbeat(timeout)` makes the library tell the
Agent, from your app's UI thread, that it is alive, 4 times per timeout. If the beats stop for
longer than the timeout, the Agent stops the app and starts it again. Which thread beats depends on
the framework: the one your UI runs on, so that a hung UI stops the beats.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

The library beats from Android's main thread.

```kotlin
withContext(Dispatchers.IO) { OhrKiosk.start(activity) }
OhrKiosk.heartbeat(15_000)   // 15 s
```

For a UI that runs on a thread of its own, call `OhrKiosk.beat(timeoutMs)` from that thread a few
times per `timeoutMs` instead: one beat, a one-way call to the Agent.

</TabItem>
<TabItem label="Java">

The library beats from Android's main thread.

```java
OhrKiosk.start(activity);      // on a background thread
OhrKiosk.heartbeat(15_000);    // 15 s
```

For a UI that runs on a thread of its own, call `OhrKiosk.beat(timeoutMs)` from that thread a few
times per `timeoutMs` instead: one beat, a one-way call to the Agent.

</TabItem>
<TabItem label="Dart">

The plugin beats from the Dart UI isolate, with a timer in the isolate that called `heartbeat`, so
a hung isolate stops the beats even while Android's main thread is fine.

```dart
await OhrKiosk.start();
await OhrKiosk.heartbeat(timeout: const Duration(seconds: 15));
```

</TabItem>
<TabItem label="TypeScript">

The module beats from the JavaScript thread. JavaScript timers stop while the app is in the
background (with the screen off, for example), so the heartbeat pauses there: when the app leaves
the `active` state, the module stops the Agent's watch, and it beats again when the app comes back.

```ts
await OhrKiosk.start();
OhrKiosk.heartbeat(15_000);   // 15 s
```

`heartbeat` returns at once; `stopHeartbeat()` returns a Promise. On an Agent older than 1061 the
beats have no effect, and `heartbeat` doesn't throw.

</TabItem>
<TabItem label="C#">

The library beats from Android's main thread, where .NET for Android and MAUI run their UI.

```csharp
await OhrKiosk.StartAsync(activity);
OhrKiosk.Heartbeat(TimeSpan.FromSeconds(15));
```

</TabItem>
</Tabs>

- The timeout is 2 seconds to 10 minutes, 10 seconds by default: `timeoutMs` in Kotlin, Java and
  TypeScript, a `Duration` or `TimeSpan` in Dart and C#. Outside that, `heartbeat` throws
  `InvalidConfig` (`field` `timeoutMs`; `timeout` in Dart).
- With Agent 1062 or later, the fleet's [response timeout](#response-timeouts) for the app, when it
  sets one, replaces the timeout the app passes. The library still beats 4 times per the app's own
  timeout, so keep the fleet's at least a quarter of it: a shorter one takes a healthy app for a
  hung one.
- It counts only while your app is pinned. Call it after `start`, and again each time your app
  starts: after a restart it is a new process.
- One heartbeat per app: calling it again replaces the last one. `stopHeartbeat()` ends it, before
  long work on the UI thread that you expect, for example.
- It may be called from the main thread: each beat is a one-way call, which doesn't wait for the
  Agent's answer. It goes on when the Agent restarts.

## Response timeouts

The fleet's **Response timeout** for an app (the setting `apps.response_timeout`) is how long the
app's main thread may stay busy before it counts as not responding, for apps slower than
Android's 5 seconds. It is a whole number of seconds, 1 to 2147483 (Android's limit), set per app:

- It is the app's "isn't responding" (ANR) time, on OhrTech OS 2026110901 and later. Earlier
  releases keep Android's 5 seconds. This applies to any app the hub installed, in kiosk mode or
  not.
- For the kiosk app, it is the watchdog's [heartbeat](#heartbeat) timeout, in place of the one the
  app passes. The app still has to call `heartbeat()` to be watched: the fleet sets only the time.
- It is the full timeout an app gets after the screen comes back on (see [the watchdog](#the-watchdog)).

A change applies at once to apps on screen; an app still starting picks it up at its next start.
It needs OhrTech Agent 1062 or later.

The value merges per app down the fleet tree: a fleet's own timeout for an app wins over its parent
fleets', a fleet that sets none takes the nearest parent fleet's, and with none at all Android's
5 seconds apply. A device's own value for an app, in its settings, wins over its fleets'.

### In the portal

Open the fleet, go to its **Applications** tab and choose **Change** next to the app. Under
**Response timeout**, type the seconds and choose **Save timeout**. **Stop setting it here** goes
back to the parent fleet's timeout, or Android's.

### With the Management API

`PUT /v1/fleets/{fleetId}/apps/{appId}/response-timeout` (needs `EditSettings`) sets this fleet's
timeout for the app, and the hub sends it to the fleet's devices straight away. In the Management
SDK (OhrTech.Management 2.3.0 or later) it is `SetResponseTimeoutAsync`, with
`GetResponseTimeoutAsync` and `ClearResponseTimeoutAsync` beside it.

```sh
curl -X PUT https://api.ohrtech.net/v1/fleets/flt_2dn47a2xa58j1txv8m28spkmyb/apps/app_7h2m9q4x1c8v3k5n6p0r2s4t6w/response-timeout \
  -H "Authorization: Bearer $OHR_TOKEN" -H "Content-Type: application/json" \
  -d '{"seconds": 30}'
```

```csharp server
var timeout = await api.SetResponseTimeoutAsync("flt_2dn47a2xa58j1txv8m28spkmyb", "app_7h2m9q4x1c8v3k5n6p0r2s4t6w",
    new SetResponseTimeoutRequest { Seconds = 30 });
```

The response, like `GET` on the same path (needs `ViewSettings`), shows what applies on the fleet:

```json
{
  "appId": "app_7h2m9q4x1c8v3k5n6p0r2s4t6w",
  "fleetId": "flt_2dn47a2xa58j1txv8m28spkmyb",
  "seconds": 30,
  "own": 30,
  "inheritedFrom": null
}
```

- `seconds`: what applies on the fleet, its own or the nearest parent fleet's; `null` for Android's
  5 seconds.
- `own`: this fleet's own timeout; `null` when it sets none. `inheritedFrom` then names the parent
  fleet `seconds` comes from.
- `DELETE` on the same path (needs `EditSettings`) removes this fleet's timeout, so the parent
  fleet's, or Android's, applies again.

The setting behind it, `apps.response_timeout`, holds every app's timeout as one object of app ids
and seconds, such as `{"app_7h2m9q4x1c8v3k5n6p0r2s4t6w": 30}`. It shows in the
[settings](/management-api/guides/settings/) like any other setting, and can be set per device
there; each app's value merges as above.

## The exit PIN

Staff sometimes need the device outside the kiosk app: to change a setting, or to look at another
app. With an exit PIN set, they open a keypad that the Agent draws over the kiosk app, type the
PIN, and kiosk mode is lifted for the fleet's **Kiosk exit time** (10 minutes by default). It also
ends when the screen turns off, or from **Back to kiosk now** in the notification. Then the same
app is pinned again.

The hub keeps only a slow salted hash of the PIN, and the device gets only that hash: the PIN
itself is stored nowhere. The Management API and the portal show only that a PIN is set:
`{"set": true}`. Without a PIN, only the hub can lift kiosk mode.

Each wrong PIN locks the keypad for longer: 30 seconds after the first, 1 minute after the second,
5 minutes after the third, then 15 minutes after each one, until the right PIN is typed. The count
is kept when the device restarts.

### Ways to open the keypad

The fleet's **Ways to open the exit PIN** (`kiosk.exit_triggers`) picks which of these work. All
four are on by default.

| Value | Portal label | How |
|---|---|---|
| `power_menu` | Exit kiosk in the power menu | An **Exit kiosk** item in the power menu |
| `keys` | A key sequence | **Exit key sequence**: volume down 5 times within 3 seconds (`volume_down_5`), or volume up and down held together for 5 seconds (`volume_both_hold`) |
| `gesture` | Taps in a corner of the screen | 5 taps within 3 seconds in the **Exit taps corner** |
| `app` | The kiosk app (Device SDK requestExit) | Your app calls `requestExit()`, from its own staff menu for example |

The power menu item and the key sequence work once the device's OhrTech OS supports them. With the
power menu item on, the power menu stays available in kiosk mode, so it also offers power off and
restart.

The corner is a square of an eighth of the screen's shorter side, at least 48 dp. The Agent
watches the taps without taking them: your app gets every touch as before.

`requestExit()` (`RequestExitAsync()` in C#) opens the keypad and returns; it needs no grant. Your
app must be the one pinned (`InvalidConfig` with `field` `kiosk` otherwise). It throws
`NotAllowed("kiosk")` when `app` isn't one of the fleet's ways, and `Unsupported` when no exit PIN
is set.

### From the hub

The hub can lift kiosk mode without the PIN, whether a PIN is set or not. In the portal, open the
device and choose **Exit kiosk mode for a while** among its tasks: 5, 10, 15, 30 or 60 minutes, or
**Back to kiosk mode now**. With the Management API (needs `EditSettings`):

```sh
curl https://api.ohrtech.net/v1/devices/dev_3swt6f457299btzpw1bxx4wf0q/kiosk/exit \
  -H "Authorization: Bearer $OHR_TOKEN" -H "Content-Type: application/json" \
  -d '{"minutes": 30}'
```

`minutes` is 1 to 240, or 0 to go back to kiosk mode now. The response is the `KioskExit`
[task](/management-api/guides/messages-and-tasks/#tasks). It fails when the device isn't in kiosk
mode (or, for 0, when kiosk mode wasn't lifted). A lift also ends when the screen turns off.

## What the person at the device sees

| When | On screen |
|---|---|
| Kiosk mode is on | Only your app, with the features it was started with |
| The keypad opens | **Exit kiosk mode**, "Enter the exit PIN.", digits, **Cancel** and **OK**. It is drawn by the Agent, so no keyboard app sees the PIN |
| A wrong PIN | "Wrong PIN.", or "Too many wrong PINs. Try again in …" while it is locked |
| Kiosk mode is lifted | The home screen, and a notification "Kiosk mode is off for now" counting down, with **Back to kiosk now** |
| The app stopped | A cover: "*App* stopped", "Starting it again in …" |
| The watchdog gave up | A cover: "*App* isn't working", "It stopped 5 times in the last 10 minutes. Your organisation has been told.", with **Try again** |

The covers and the keypad are system windows above every app, the notification shade and the lock
screen: the kiosk app can't hide them. When an exit PIN is set and at least one way to open it is
on, the covers also have an **Exit kiosk** button that opens the keypad.

## Grants and errors

`start` and `stop` need the fleet's `kiosk` grant (`NotAllowed("kiosk")` without it). `state`,
the mode changes, `requestExit` and `heartbeat` don't.

| Exception | When |
|---|---|
| `NotAllowed("kiosk")` | No `kiosk` grant; `stop()` when the fleet keeps kiosk apps in; `requestExit()` when `app` isn't one of the ways |
| `InvalidConfig` | `start` with a task that isn't your app's; `requestExit()` when your app isn't pinned; a heartbeat timeout outside 2 seconds to 10 minutes |
| `Unsupported` | `requestExit()` with no exit PIN; `requestExit` or `heartbeat` on an Agent older than 1061 (`heartbeat` not in TypeScript) |
| `Failed` | Android didn't lock the task; in Dart and TypeScript, `start` with no activity |

These are the Kotlin and Java names (`OhrException.NotAllowed`, ...). Dart and TypeScript name them
`OhrNotAllowed`, `OhrInvalidConfig`, ...; C# `OhrNotAllowedException`, `OhrInvalidConfigException`,
... See [errors](/device-sdk/access/#errors).
