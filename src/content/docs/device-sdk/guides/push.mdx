import { Tabs, TabItem } from '@astrojs/starlight/components';

Your server can wake your app on a device and hand it a message: a new order, a changed price list,
a request to sync. The message is sealed to a key in the device's TEE and signed with your server's
key. The OhrTech hub and the OhrTech Agent carry it but can't read it, and your app accepts only
messages your server signed. No Google services are involved.

The steps:

1. The app says what receives the messages: in Kotlin and Java, a push service it declares; in
   Flutter, React Native and .NET, handlers it gives the library, which declares the service itself.
2. The app registers once, with your server's public sender keys. It gets a token (`psh_…`) and a
   public key, and sends both to your server.
3. Your server seals and signs each message and sends it with `POST /v1/push`. See
   [send push messages](/device-sdk/server/send-push/).
4. The library checks each message and passes the good ones to your `onMessage`.

Push is open to every app your organisation installed through OhrTech: no fleet grant is needed. It
needs OhrTech Agent 1059 or later and OhrTech OS 2026110702 or later, the OS with the OhrTech KEM
app in the TEE. On an older OS, `register` throws `OhrException.Unsupported` (`OhrUnsupported` in
Dart and TypeScript, `OhrUnsupportedException` in C#).

## Choose a suite

A token has one suite, chosen when the app registers. Your server must seal with that suite.

| | `x25519` (default) | `xwing-mldsa65` |
|---|---|---|
| Encryption | HPKE with X25519 | HPKE with X-Wing (ML-KEM-768 and X25519) |
| Your server signs with | Ed25519 | Ed25519 and ML-DSA-65; both must verify |
| Size added to your data | About 175 bytes, plus the length of your message id | About 4.6 KB |
| The app's public key | 32 bytes | 1,216 bytes |
| Use it for | Most messages: wake-ups, notices, ids to fetch | Content that must stay secret for years, even against a future quantum computer |

Either way, a message carries up to 4,096 bytes of your data.

## Declare the push service

The Agent hands each message to the app's push service, a service only the Agent may bind. An app
has one.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

Subclass `OhrPushService`:

```kotlin
import android.util.Log

class Push : OhrPushService() {
    override fun onMessage(message: OhrPushMessage) {
        val json = String(message.data)          // your bytes, as your server sealed them
        Log.i("Push", "${message.id}: $json")
    }

    override fun onDropped(pushId: String, reason: String) {
        Log.w("Push", "Dropped $pushId: $reason")
    }
}
```

Declare it in your manifest, protected by the `RECEIVE_PUSH` permission. Only the OhrTech Agent holds
that permission, so no other app can feed your service messages:

```xml
<service
    android:name=".Push"
    android:exported="true"
    android:permission="net.ohrtech.device.permission.RECEIVE_PUSH">
    <intent-filter>
        <action android:name="net.ohrtech.device.action.PUSH" />
    </intent-filter>
</service>
```

The Agent refuses to deliver to a push service that doesn't require this permission. Its messages are
dropped with the reason `push_service_unprotected`.

The callbacks run one at a time on a worker thread of the service, so they may make blocking calls,
such as `OhrPush.register` from `onTokenChanged`.

<TabItem label="Dart">

The plugin declares the push service in its manifest; don't declare one of your own. Write the
handlers as top-level functions, annotated `@pragma('vm:entry-point')`, and give them to
`OhrPush.setHandlers` in `main()`, before `runApp`:

```dart
@pragma('vm:entry-point')
Future<void> onPushMessage(OhrPushMessage message) async {
  final json = utf8.decode(message.data);        // your bytes, as your server sealed them
  debugPrint('${message.id}: $json');
}

@pragma('vm:entry-point')
Future<void> onPushDropped(String pushId, String reason) async {
  debugPrint('Dropped $pushId: $reason');
}

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await OhrPush.setHandlers(onMessage: onPushMessage, onDropped: onPushDropped);
  runApp(const MyApp());
}
```

The handlers run in a background isolate, whether the app is open or not. The plugin starts that
isolate, with no UI, for the first message and keeps it while the process lives. It shares no
memory with your UI's isolate, so pass results on through storage, or a port registered with
`IsolateNameServer`. A message that starts the app doesn't run `main()`: the plugin keeps the
handlers' callback handles from the last `setHandlers`, so call it at every start. A closure or an
instance method has no handle; `setHandlers` throws `OhrInvalidConfig` for one.

</TabItem>


The handlers run as a headless JS task, whether the app is open or not. If it isn't, React Native
starts for the task without mounting your app's component; `index.js` runs, so the handlers are
set. If it is, the task runs in the app's JavaScript context, next to its UI.

### When the app isn't running

The Agent binds the push service, and Android starts the app's process for it, without UI: the
app's `Application` first, then the service. In Flutter, the plugin then starts the background
isolate; in React Native, React Native starts and `index.js` runs. The app doesn't have to be open.

Messages reach the handlers one at a time. The Agent lets go of the service about 30 seconds after
the last message. In Flutter, React Native and .NET the service waits for each handler, up to 25
seconds, so the process stays up while it works. For longer work, start a foreground service or
WorkManager work.

In Flutter, React Native and .NET, set the handlers before any message arrives, as above.

A message that doesn't reach your handler isn't lost silently: your server sees it as `dropped`,
and the library forgets its `id`, so your server may send it again (net.ohrtech:device-sdk 0.3.2
and the 0.1.1 wrappers). That covers no handler set, a handler that throws or takes longer than 25
seconds, and React Native or the Flutter background isolate failing to start; see
[dropped messages](#dropped-messages) for the reasons. In Kotlin and Java, throw from `onMessage`
when the app couldn't take the message; throw `OhrPushService.NotHandled(reason)` to say why.

| Handler | |
|---|---|
| `onMessage(message)` | A message that passed every check. Required |
| `onDropped(pushId, reason)` | A message the library refused, and why (see [dropped messages](#dropped-messages)) |
| `onTokenChanged(token)` | For a token that ended at OhrTech (`null`: register again if you still want push); see [when a token ends](#when-a-token-ends) |
| `senderKeys()` | Kotlin and Java only: the keys messages must be signed with. By default, the ones you gave `register` or `setSenderKeys` |

In C#, `SetHandlers` takes `onMessage`, `onTokenChanged` and `onDropped`; MAUI's options are
`OnPushMessage`, `OnPushTokenChanged` and `OnPushDropped`.

| Message | |
|---|---|
| `id` | Your server's id for the message |
| `data` | Your bytes, at most 4,096 |
| `expiresAtMs` | When it expires, as your server sealed it (Unix milliseconds). Dart: `expiresAt`, a `DateTime` |
| `highPriority` | Sent with priority `high` |
| `pushId` | The hub's id for this delivery (`pmsg_…`). Your server can look it up |

The class is `OhrPushMessage` in every language. In C# its properties are `Id`, `Data`,
`ExpiresAt` (a `DateTimeOffset`), `HighPriority` and `PushId`.

## Register

Register once, with your server's sender public keys, and send the token to your server. The sender
keys are public; build them into the app, or deliver them with
[managed configuration](/device-sdk/guides/managed-config/). An app may register 5 times an hour
(Agent 1063, and the hub allows 10): past that, `register` throws `Failed`; try again later.

```kotlin
sendToServer(token.token, token.suite.wireName, token.publicKeyBase64)
```

Send your server three things from the token:

- the token (`psh_…`): what your server sends to;
- the suite's name, `x25519` or `xwing-mldsa65`: `suite.wireName` in Kotlin and Java,
  `suite.wire` in Dart, `suite` in TypeScript, `Suite.WireName` in C# (`Suite` is the enum
  `OhrPushSuite`);
- the public key, base64: what your server seals to. `publicKeyBase64` (C#: `PublicKeyBase64`);
  in TypeScript, `publicKey` is base64 already.

Registering again makes a new key and a new token, and ends the old token. Messages still on their
way to the old token are dropped. So don't register on every start: ask for the token first, as
above, and register only when there is none.

Set the sender keys on every start. It is cheap and local, and the library keeps the keys in the
app's own storage, which "Clear storage" in Android's settings empties. Without them every message
is dropped with `signature`. Alternatively, in Kotlin and Java, override `senderKeys()` in your
service to return constants.

| Kotlin, Java | Dart, TypeScript | C# | |
|---|---|---|---|
| `register(senderKeys, suite = X25519)`, `registerAsync` (Kotlin) | `register(senderKeys, suite)` (Dart: `suite:`) | `RegisterAsync(senderKeys, suite)` | Makes the key and the token; ends any old token |
| `token()` | `token()` | `GetTokenAsync()` | The current token, or `null` |
| `unregister()` | `unregister()` | `UnregisterAsync()` | Ends the token and deletes the push key |
| `setSenderKeys(keys)`, `senderKeys()` | `setSenderKeys(keys)`, `senderKeys()` | `SetSenderKeys(keys)`, `GetSenderKeys()` | The keys messages must be signed with |
| `OhrPushService` | `setHandlers(…)` | `SetHandlers(…)` | What receives the messages (see [above](#declare-the-push-service)) |

A sender key is `SenderKey.fromBase64(ed25519, mlDsa65)` in Kotlin and Java,
`OhrSenderKey.fromBase64` in Dart, `OhrSenderKey.FromBase64` in C#, and in TypeScript an object
`{ ed25519, mlDsa65? }` of base64 strings (`senderKey(ed25519, mlDsa65)` makes one from bytes).

| Error | When |
|---|---|
| `OhrException.InvalidConfig` | No sender keys, or `xwing-mldsa65` with no sender key that has ML-DSA-65 (`field` is `senderKeys`); a key of the wrong size (`ed25519`, `mlDsa65`) |
| `OhrException.Unsupported` | The device's OS has no OhrTech KEM app |
| `OhrException.Failed` | The hub can't be reached or didn't answer in 30 seconds (try again later), or it refused the key (`The hub refused: …`) |
| `OhrException.NotManaged` | Your organisation didn't install this app through OhrTech |

The table names the Kotlin and Java classes. In Dart and TypeScript they are `OhrInvalidConfig`,
`OhrUnsupported`, `OhrFailed` and `OhrNotManaged`; in C#, `OhrInvalidConfigException`,
`OhrUnsupportedException`, `OhrFailedException` and `OhrNotManagedException`.

The library checks the key sizes: an Ed25519 public key is 32 bytes, an ML-DSA-65 public key 1,952.
In Kotlin and Java it checks when you make the `SenderKey`; in the other languages, when you
register or set the keys.

## What the library checks

Before `onMessage`, the library checks that:

1. The envelope is well formed, version 1, and for the app's current token.
2. Its suite is the token's.
3. One of the sender keys made every signature the suite has: Ed25519, and for `xwing-mldsa65`
   ML-DSA-65 too.
4. It opens with the app's key in the TEE. The app opens it through the Agent; neither the app nor
   the Agent ever holds the private key.
5. It hasn't expired, by the device's clock, with 2 minutes' grace.
6. Its `id` wasn't seen before. The library remembers ids until they expire, so your server can send
   the same message again safely. It keeps up to 2,000 ids; with more, the ones that expire soonest
   go first.

The checks run in the library's own code, in Flutter, React Native and .NET too, before your
handler. A message that fails a check never reaches `onMessage`. The library drops it, tells the
hub why, and calls `onDropped`.

### Dropped messages

| `reason` | Why |
|---|---|
| `malformed` | Not a push envelope, or what it sealed isn't a push message |
| `token` | It is for a token the app no longer has |
| `suite` | It was sealed with the other suite |
| `signature` | None of the sender keys signed it |
| `does_not_open` | It wasn't sealed to this app's key |
| `expired` | Its expiry passed, plus 2 minutes |
| `duplicate` | Its `id` was seen before |
| `agent` | The OhrTech Agent failed while opening it, for example because it stopped |
| `handler` | Your handler threw (or, in Flutter, its callback wasn't found after an update) |
| `handler_timeout` | Flutter, React Native and .NET: your handler took longer than 25 seconds |
| `no_handler` | Flutter, React Native and .NET: no handlers were set when it arrived |
| `no_engine` | Flutter and React Native: the background isolate or React Native didn't start |
| your own | Kotlin and Java: the reason of the `OhrPushService.NotHandled` your `onMessage` threw |

The last five never reach `onDropped`: the message passed every check, and the app didn't take it.
The library forgets its `id`, so sending it again isn't a duplicate.

Your server sees these as the message's `dropped` status, with `app_` before the reason (for example
`app_signature`). The Agent also drops some messages before they reach the app, for example when
the app has no push service (`no_push_service`) or Android can't start it (`bind_failed`). See
[message statuses](/device-sdk/server/send-push/#follow-a-message).

## Priority and Doze

Your server sends each message as `normal` (the default) or `high`.

- **`high`**: before it delivers, the Agent puts your app on Android's temporary power allowlist for
  20 seconds. That exempts it from Doze, and lets it start a foreground service from the background.
  Use it for what the user or the business is waiting for.
- **`normal`**: delivered the same way, without the exemption. A foreground service start from
  `onMessage` may be refused, so use WorkManager.

`message.highPriority` (C#: `HighPriority`) tells you which one it was.

## Expiry and duplicates

A message has two expiry times, set by your server:

- The **expiry inside the sealed message**. The library drops the message after it (plus 2 minutes'
  grace), however it arrived.
- The **`ttl`** of the send, 1 second to 28 days (default 1 day). The hub keeps trying until then,
  and the Agent drops a message that reaches the device later.

The hub sends a message again until the Agent acknowledges it, so the same message can arrive
twice. The library drops the repeat as `duplicate`. Give each new message a new `id`, and keep the
`id` when you send the same message again.

## Rotate keys

**Your server's sender keys.** The library accepts a message signed by any key in its list, so
rotate in three steps:

1. Ship the new key next to the old one: `setSenderKeys([oldKey, newKey])`.
2. When the apps have it, sign with the new key.
3. Drop the old key: `setSenderKeys([newKey])`.

**The app's push key.** Call `register` again. The app gets a new key and token, the old token ends,
and messages still queued for it are dropped. Send the new token to your server.

## When a token ends

| What happened | What to do |
|---|---|
| The app registered again | Use the new token |
| The app called `unregister()` | Nothing. Register again to receive messages |
| The app was uninstalled | Nothing. The token and the app's keys are deleted with it |
| The device moved to a fleet without the app, or the app was removed from the device's fleet | The token ends at the next message your server sends to it; the app's `onTokenChanged(null)` follows |

Your server learns that a token ended when `POST /v1/push` refuses a message with
`the token has ended (…)`. Then drop the token, and wait for the app to send a new one.

When OhrTech ends a token the app didn't end itself, the device learns it right away if it is
online, or at its next connection, and your `onTokenChanged` handler runs with `null`, the app
started for it if it isn't running: register again if the app still wants push, and send the new
token to your server. Asking for the token when the app starts, as in [Register](#register), covers
the rest.
