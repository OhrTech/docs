import { Tabs, TabItem } from '@astrojs/starlight/components';

The OhrTech Agent judges every call your app makes: who the app is, and what its fleet lets it
do. This page covers those rules, the exceptions you get when a call can't go through, how to call
the SDK from the right thread, how it follows the Agent, and which Agent versions each area needs.

Calls are named here as in Kotlin. The Flutter, React Native and .NET SDKs have the same ones in
their own style: `OhrWifi.state()` is `OhrWifi.state()` in Dart and TypeScript too, and
`OhrWifi.GetStateAsync()` in C#.

## Who may use what

Only apps your organisation installed on the device through OhrTech may use the Device SDK. The
Agent also checks that the installed APK is still signed with the key it was installed with. Any
other caller gets `OhrException.NotManaged`, on `OhrDeviceSdk.connect` and on every call.

A managed app may read most things and use the areas that only touch itself. Changing the device
needs the fleet's **grant** for that area:

| Area | Every managed app | With the fleet's grant |
|---|---|---|
| `device` | `OhrDevice.info()` | |
| `updates` | `OhrUpdates.available()`, `install()`, `changes` | |
| `wifi` | `OhrWifi.state()`, `networks()`, `scan()`, `saved()`, `stateChanges`, `networkChanges` | `save`, `connect`, `disconnect`, `forget`, `setEnabled`, `connectQr`, and [`OhrWifiView`](/device-sdk/guides/wifi-and-networks/) |
| `network` | `OhrNetwork.state()`, `changes` | `setMobileData`, `setAirplaneMode`, `setDataRoaming` |
| `kiosk` | `OhrKiosk.state()`, `modeChanges`, `requestExit()`, `heartbeat()`, `beat()` | `start`, `stop` |
| `power` | `OhrPower.battery()`, `rebootSchedule()`, `batteryChanges` | `reboot`, `scheduleReboot`, `setScreenTimeout`, `setBrightness` |
| `settings` | `OhrSettings.keys()`, `get()`, `changes` | `set` |
| `keys`, `push`, `diagnostics`, `usb`, `certificates` | Everything | |
| `config`, `attestation` | Everything: they don't go through the Agent's grants | |

The areas a fleet can grant are `wifi`, `network`, `kiosk`, `power` and `settings`. `usb` and
`certificates` need no grant, but they give your app only what the fleet sets up for it: the
[USB devices](/device-sdk/guides/usb-devices/) it approves, the
[certificates and CAs](/device-sdk/guides/certificates/) it gives the app.

Some calls also follow other fleet settings, whatever the grant: `OhrKiosk.stop()` works only if the
fleet lets kiosk apps leave, and `OhrKiosk.requestExit()` only if the fleet lets the app offer the
exit PIN. Both throw `OhrException.NotAllowed("kiosk")` otherwise. See [kiosk mode](/device-sdk/guides/kiosk/).

## Grant an area

A grant is per fleet and per app: the fleet setting `sdk.access`. It applies to the fleet's devices
and to the fleets below it, unless a fleet below has a grant of its own for that app.

- **Portal:** open the fleet, then its **Applications** tab. The **Device SDK** column shows what
  each app may change; **Change** on an app's row turns areas on and off.
- **Management API:** `GET`, `PUT` and `DELETE /v1/fleets/{fleetId}/apps/{appId}/sdk-access`.
  Reading needs `ViewSettings`; changing needs `EditSettings` ([permissions](/management-api/permissions/)).

<Tabs syncKey="lang">

```csharp server
var access = await api.SetSdkAccessAsync("flt_2dn47a2xa58j1txv8m28spkmyb", "app_7h2m9q4x1c8v3k5n6p0r2s4t6w",
    new SetSdkAccessRequest { Areas = ["wifi", "kiosk"] });
Console.WriteLine(string.Join(", ", access.Areas)); // "wifi, kiosk"
```

`GetSdkAccessAsync` reads the grant; `ClearSdkAccessAsync` drops the fleet's own grant.

</TabItem>


</TabItem>

`PUT` replaces the fleet's grant for the app with the areas you send. It answers with the grant as
it now applies, as `GET` does:

```json
{
  "appId": "app_7h2m9q4x1c8v3k5n6p0r2s4t6w",
  "fleetId": "flt_2dn47a2xa58j1txv8m28spkmyb",
  "areas": ["wifi", "kiosk"],
  "own": ["wifi", "kiosk"],
  "inheritedFrom": null,
  "alwaysAllowed": ["device", "updates", "keys", "push", "wifi.read", "network.read", "power.read", "settings.read"]
}
```

| Field | |
|---|---|
| `areas` | What the app may change on this fleet's devices: the fleet's own grant, or the nearest parent fleet's |
| `own` | This fleet's own grant, or null when it has none and inherits |
| `inheritedFrom` | The fleet whose grant applies when `own` is null |
| `alwaysAllowed` | What the app may use without a grant |

| To | Send |
|---|---|
| Grant areas | `PUT` with the areas. They are kept in the order `wifi`, `network`, `kiosk`, `power`, `settings`, each once |
| Take away what a parent fleet grants | `PUT` with `{"areas": []}` |
| Inherit the parent fleet's grant again | `DELETE` |

An area that isn't one of the five is refused with 400 "Bad areas". A fleet or app you can't reach
is 404 "No such fleet" or "No such app". The fleet's devices get the change when they are next
online.

## Check before you call

`OhrAccess.info()` asks the Agent who your app is and what it may use. Its `areas` are the
always-allowed areas, the reads (`wifi.read`, `network.read`, `power.read`, `settings.read`) and
each area the fleet grants. `mayUse(area)` checks one; `OhrAccess.mayUse(area)` asks the Agent for
that one area.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val access = OhrAccess.infoAsync()            // asks the Agent now
show("${access.app} may use ${access.areas}")
val canChangeWifi = access.mayUse("wifi")     // or OhrAccess.mayUseAsync("wifi")
```

</TabItem>
<TabItem label="Java">

```java
// On a background thread
OhrAccess.Info access = OhrAccess.info();     // asks the Agent now
show(access.getApp() + " may use " + access.getAreas());
boolean canChangeWifi = access.mayUse("wifi"); // or OhrAccess.mayUse("wifi")
```

</TabItem>
<TabItem label="Dart">

```dart

show('${access.app} may use ${access.areas}');
final canChangeWifi = access.mayUse('wifi');  // or await OhrAccess.mayUse('wifi')
```

</TabItem>
<TabItem label="TypeScript">

```ts

console.log(`${access.app} may use ${access.areas.join(', ')}`);
const canChangeWifi = access.areas.includes('wifi');   // or await OhrAccess.mayUse('wifi')
```

</TabItem>
<TabItem label="C#">

```csharp

```

</TabItem>
</Tabs>

Use it to decide what to show. The answer is the fleet's grant as it is when you ask; the Agent
still checks every call against the grant as it is at that moment, so a grant taken away since makes
the next change throw `OhrException.NotAllowed`. Ask again when you need to know again.

Every change an app makes through the Device SDK, and every change the Agent refuses, is recorded
in the device's events: on the device's page in the portal, and with
`GET /v1/devices/{deviceId}/events`. Each event names the app, the area, the action and the result:
`ok`, `failed` (Android refused), `denied` (not granted), `locked` (the fleet locks it) or
`dropped` (a push message the library dropped). A refusal
of the same app, area and action is recorded at most once an hour.

## Settings the fleet locks

A grant lets the app change what the fleet leaves open, not what it locks. A change to a setting the
fleet **locks** throws `OhrException.FleetLocked`, whose `key` is the setting's key in the
[settings catalogue](/management-api/guides/settings/):

| Call | Refused when the fleet locks |
|---|---|
| `OhrSettings.set(key, value)` | `key` |
| `OhrPower.setScreenTimeout` | `display.timeout` |
| `OhrPower.setBrightness` | `display.brightness` |
| `OhrNetwork.setDataRoaming` | `network.data_roaming` |
| `OhrWifi.setEnabled` | `wifi.enabled` |
| `OhrWifi.save`, `connect(config)`, `connectQr`, `forget` for one of the fleet's own networks | `wifi.networks` (the fleet's networks are read-only to apps) |

`OhrSettings.get(key)` tells you beforehand: its `mode` is `unmanaged`, `set` or `locked`, and
`locked` is true for `locked`. A setting the fleet only sets (`set`) is open: the app's change holds
until the fleet changes that setting. Some settings, such as the lock screen, debugging and factory
reset, are never open to apps; `OhrSettings.keys()` lists the ones that are. See
[device, power and settings](/device-sdk/guides/device-power-settings/).

## Errors

Every refusal or failure is an `OhrException`, never a raw binder or platform exception. Each SDK
has the same seven:

| Kotlin and Java (`OhrException.…`) | Dart and TypeScript | C# | Properties | When |
|---|---|---|---|---|
| `NotManaged` | `OhrNotManaged` | `OhrNotManagedException` | | The app isn't one your organisation installed on this device through OhrTech, or no longer carries the signature it was installed with |
| `NotAllowed` | `OhrNotAllowed` | `OhrNotAllowedException` | `area` | The fleet doesn't grant the area (`"wifi"`, `"kiosk"`, ...), or a kiosk call the fleet doesn't allow (`stop`, `requestExit`) |
| `FleetLocked` | `OhrFleetLocked` | `OhrFleetLockedException` | `key` | The fleet locks the setting or network `key` ([above](#settings-the-fleet-locks)) |
| `Unsupported` | `OhrUnsupported` | `OhrUnsupportedException` | `reason`, `needsAgent` | The device, its OS or its Agent can't do it: no OhrTech Agent, an OS without TEE keys, a setting key apps can't use, no update offered to install, no exit PIN set. When the Agent is only too old, `needsAgent` is the Agent version that can ([versions](#agent-versions)); otherwise it is null |
| `InvalidConfig` | `OhrInvalidConfig` | `OhrInvalidConfigException` | `field`, `reason` | A value the app passed is wrong: `field` names it, `reason` says why ([below](#values-the-library-refuses)) |
| `Failed` | `OhrFailed` | `OhrFailedException` | `reason` | The Agent tried and Android refused; or the Agent can't be reached, stopped during the call (the library binds again: try again), didn't answer in time; or the hub didn't answer in time (push registration, a certificate request); or anything else unexpected |
| `Refused` | `OhrRefused` | `OhrRefusedException` | `reason` | The hub refused a certificate request it checks itself, such as when the fleet gives the app no issuing CA ([certificates](/device-sdk/guides/certificates/)) |

In C# the properties are `Area`, `Key`, `Reason`, `NeedsAgent` and `Field`.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
try {
    withContext(Dispatchers.IO) { OhrPower.setBrightness(80) }
} catch (e: OhrException.NotAllowed) {
    show("the fleet doesn't grant ${e.area}")        // "power"
} catch (e: OhrException.FleetLocked) {
    show("the fleet locks ${e.key}")                 // "display.brightness"
} catch (e: OhrException.Unsupported) {
    e.needsAgent?.let { show("needs Agent $it") }
} catch (e: OhrException) {
    show("brightness: ${e.message}")
}
```

`OhrException` is a sealed class, so `when (e)` can cover every case.

</TabItem>
<TabItem label="Java">

```java

}
```

</TabItem>
<TabItem label="Dart">

```dart

  show('the fleet locks ${e.key}');                  // 'display.brightness'
} on OhrUnsupported catch (e) {

}
```

`OhrException` is a sealed class, so a `switch` on it can cover every case.

</TabItem>
<TabItem label="TypeScript">

```ts

} catch (e) {
  if (e instanceof OhrNotAllowed) {
    console.log(`the fleet doesn't grant ${e.area}`);    // 'power'
  } else if (e instanceof OhrFleetLocked) {
    console.log(`the fleet locks ${e.key}`);             // 'display.brightness'
  } else if (e instanceof OhrUnsupported) {
    if (e.needsAgent !== null) console.log(`needs Agent ${e.needsAgent}`);
  } else if (e instanceof OhrException) {
    console.warn(`brightness: ${e.code}: ${e.message}`);
  }
}
```

Each class has a `code` too (`'NotManaged'`, `'NotAllowed'`, ...), for code that switches on it.

</TabItem>

### Values the library refuses

Some values the library checks itself, before it asks the Agent. They throw
`OhrException.InvalidConfig` too, with `field` naming the value:

| Call | `field` | Allowed |
|---|---|---|
| `OhrKiosk.heartbeat`, `OhrKiosk.beat` | `timeoutMs` (`timeout` in Dart) | 2 seconds to 10 minutes |
| `OhrDiagnostics.event` | `name`, `data` | A name of `a-z` first, then up to 63 of `A-Z a-z 0-9 _ .`; data up to 2 KB as JSON |
| `OhrCertificates` calls with an alias | `alias` | 1 to 64 of `A-Z a-z 0-9 . _ -` |
| `OhrAttestation.attest` | `challenge` | 1 to 128 bytes |
| `OhrPush.register` | `senderKeys` | At least one sender key, with an ML-DSA-65 key for `xwing-mldsa65` |

The Agent refuses wrong values of its own the same way: a Wi-Fi config's field, a screen timeout's
`seconds`, a brightness `percent`.

## Threading

Calls into the Agent are binder calls: they block until the Agent answers. Some take seconds (a Wi-Fi
connection, `OhrPush.register` up to 30 seconds, `OhrCertificates.request` up to 60 seconds).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

Make blocking calls off the main thread. The library marks them `@WorkerThread`, so lint can flag
calls from the main thread.

```kotlin
// Suspending versions, safe on the main thread
OhrDeviceSdk.connect()
val info = OhrDevice.infoAsync()
val mayChangePower = OhrAccess.mayUseAsync("power")
val token = OhrPush.registerAsync(listOf(SenderKey.fromBase64(ED25519_PUBLIC_KEY)))

// Everything else: move it to Dispatchers.IO
val battery = withContext(Dispatchers.IO) { OhrPower.battery() }
```

The suspending versions are `OhrDeviceSdk.connect`, `OhrDevice.infoAsync()`,
`OhrAccess.infoAsync()` and `mayUseAsync()`, and `OhrPush.registerAsync()`. Flows do their binder
calls on `Dispatchers.IO` themselves, wherever you collect them.

</TabItem>
<TabItem label="Java">

Make every call on a thread of your own. The library marks the blocking ones `@WorkerThread`, so
lint can flag calls from the main thread.

```java
executor.execute(() -> {
    try {
        OhrPower.Battery battery = OhrPower.battery();
        activity.runOnUiThread(() -> show(battery));
    } catch (OhrException e) {
        // see Errors
    }
});
```

</TabItem>
<TabItem label="Dart">

Every call returns a `Future`. The plugin makes the binder call on a thread of its own, never on
Flutter's UI thread, so call it from anywhere.

```dart
final battery = await OhrPower.battery();
show('${battery.level}%');
```

</TabItem>
<TabItem label="TypeScript">

Every call returns a `Promise`. The module makes the binder call on a worker thread, never on the
JavaScript thread or the UI thread, so call it from anywhere.

```ts
const battery = await OhrPower.battery();
console.log(`${battery.level}%`);
```

</TabItem>
<TabItem label="C#">

Every call that asks the Agent is an `…Async` method that makes the binder call on the thread pool,
so `await` it from the UI thread. Events are raised on the `SynchronizationContext` of the code that
added the handler, which is the UI thread in an activity or a MAUI page; without one, on the thread
pool.

```csharp
var battery = await OhrPower.GetBatteryAsync();
label.Text = $"{battery.Level}%";   // back on the UI thread
```

</TabItem>
</Tabs>

A first call on the main thread doesn't deadlock: the library answers the binding on a thread of its
own. It still waits for the Agent, so in Kotlin and Java connect up front off the main thread if your
app's first call has to be made there. These are safe on any thread, the main one included:

- `OhrDeviceSdk.isAvailable()` and `OhrDeviceSdk.connection`
- `OhrConfig`: it reads Android's application restrictions, not the Agent
- `OhrDiagnostics.event(...)` and `log(...)`, `OhrKiosk.heartbeat()`, `beat()` and `stopHeartbeat()`:
  one-way calls that don't wait for the Agent to act. Before the library has connected they wait for
  it to bind, as every call does.

## Following changes

Areas that change on their own tell you when they do:

| Area | Kotlin `Flow`, Dart `Stream` | Java listener | TypeScript listener | C# event | Gives |
|---|---|---|---|---|---|
| `updates` | `changes` | `listen` | `addChangeListener` | `Changed` | `OhrUpdates.Update`; `OhrUpdates.NONE` (version code 0) when the offer is withdrawn |
| `wifi` | `stateChanges` | `listenState` | `addStateListener` | `StateChanged` | `OhrWifi.State` |
| `wifi` | `networkChanges` | `listenNetworks` | `addNetworksListener` | `NetworksChanged` | The networks around |
| `network` | `changes` | `listen` | `addChangeListener` | `Changed` | `OhrNetwork.State` |
| `kiosk` | `modeChanges` | `listenMode` | `addModeListener` | `ModeChanged` | The device's lock task mode: `"none"`, `"locked"` or `"pinned"` |
| `power` | `batteryChanges` | `listenBattery` | `addBatteryListener` | `BatteryChanged` | `OhrPower.Battery` |
| `settings` | `changes` | `listen` | `addChangeListener` | `Changed` | `OhrSettings.Setting`, one key at a time |
| `config` | `changes` | `listen` | `addChangeListener` | `Changed` | The new managed configuration |
| `usb` | `changes` | `listen` | `addChangeListener` | `Changed` | `OhrUsb.Change`: an approved device attached or detached |
| `certificates` | `changes` | `listen` | `addChangeListener` | `Changed` | Nothing: the fleet changed the app's certificates or CAs |

In C#, the areas with a state also have an `IAsyncEnumerable` stream, ended by its cancellation
token: `OhrUpdates.Changes`, `OhrWifi.StateChanges` and `NetworkChanges`, `OhrNetwork.Changes`,
`OhrKiosk.ModeChanges`, `OhrPower.BatteryChanges`, `OhrSettings.Changes`.


</TabItem>

</TabItem>

</TabItem>
<TabItem label="TypeScript">

</TabItem>
<TabItem label="C#">

```csharp

// Later, to stop: a static event holds its handlers

```

A watch the Agent refuses raises `OhrDeviceSdk.EventFailed`, whose `Event` names the event and
`Error` is the `OhrException`. A stream throws it from `await foreach`.

</TabItem>
</Tabs>

- A watch gives the changes from then on, not the current value: read the current state first, as
  above.
- In Kotlin and Java, each `collect` and each `listen` is a watch of its own with the Agent. In Dart,
  TypeScript and C#, one watch per stream or event serves every listener, from the first to the last
  one removed; in C#, each `await foreach` is one of its own.
- Watches go on when the Agent restarts: the library watches again once the Agent is back. Then the
  ones that follow a state (updates, Wi-Fi state and networks, network, kiosk mode, battery) give
  the current state, for what changed meanwhile, and `certificates` tells you to read them again.
- `OhrConfig`'s changes come without the Agent: they follow Android's application restrictions.

## The connection

There is nothing to connect or close. The library binds the Agent on the first call, keeps the
binding for the life of the app's process, and binds again when the Agent stops (it crashed, or it
was updated). Calls made while the Agent is away wait for it, up to 10 seconds. To know how it
stands, for a "waiting for the device" banner say, follow the connection:

| State | Kotlin and Java (`OhrDeviceSdk.Connection`), TypeScript | Dart (`OhrConnection`) | C# (`OhrConnection`) |
|---|---|---|---|
| Nothing has asked the Agent anything yet | `NOT_CONNECTED` | `notConnected` | `NotConnected` |
| Binding the Agent for the first time | `CONNECTING` | `connecting` | `Connecting` |
| Connected | `CONNECTED` | `connected` | `Connected` |
| The Agent stopped; calls wait for it to come back | `RECONNECTING` | `reconnecting` | `Reconnecting` |
| No OhrTech Agent with the Device SDK, or the hub didn't install this app | `UNAVAILABLE` | `unavailable` | `Unavailable` |

```csharp
OhrDeviceSdk.ConnectionChanged += OnConnectionChanged;          // then each change, on this thread's context

    label.Text = e.Connection == OhrConnection.Reconnecting ? "Waiting for the OhrTech Agent" : "";
```

Following the connection doesn't bind the Agent: it stays `NOT_CONNECTED` until the first call, or
until you connect up front with `OhrDeviceSdk.connect()` (`connectBlocking()` in Java,
`ConnectAsync()` in C#). `connect` throws what the first call would: `Unsupported` with no Agent,
`NotManaged` when the hub didn't install the app, `Failed` when the Agent doesn't answer in time.

## Agent versions

Each SDK version works with every Agent version; what an older Agent lacks, the library refuses
before calling it. `OhrAccess.info().agentVersion` is the Agent's version and `agentInterface` the
Device SDK interface it speaks. The library speaks interface 2 (`OhrDeviceSdk.VERSION` in Kotlin
and Java).

| What | Needs |
|---|---|
| `OhrDeviceSdk`, `OhrAccess`; `OhrDevice`, `OhrUpdates`, `OhrWifi`, `OhrNetwork`, `OhrPower`, `OhrSettings`; `OhrKiosk.start`, `stop`, `state`, `modeChanges`; `OhrWifiView` | Agent 1059 or later (interface 1) |
| `OhrKeys`, `OhrPush` | Agent 1059 or later, on OhrTech OS 2026110702 or later (the TEE's KEM app) |
| `OhrKiosk.requestExit`, `heartbeat`, `beat` (the exit PIN and the watchdog) | Agent 1061 or later (interface 2) |
| `OhrDiagnostics` | Agent 1061 or later (interface 2) |
| `OhrUsb` | Agent 1061 or later (interface 2) |
| `OhrCertificates` | Agent 1061 or later (interface 2) |
| `OhrConfig` | Agent 1061 or later sets the values. `OhrConfig` never calls the Agent and never throws `Unsupported`: with an older Agent it gives the declared defaults |
| `OhrAttestation` | Doesn't call the Agent: it uses your app's Android Keystore. See [device attestation](/device-sdk/guides/attestation/) for what the device needs |
| The fleet's response timeout for an app, and the kiosk watchdog not counting hangs while the screen is off | Agent 1062 or later. Nothing to call: the Agent applies them ([kiosk mode](/device-sdk/guides/kiosk/)) |

On an Agent older than 1061, the interface 2 calls throw `OhrException.Unsupported` with
`needsAgent = 1061`, so you can tell an old Agent from a device that can't do it:

The Management API shows each device's Agent version
([devices and fleets](/management-api/guides/devices-and-fleets/)). Besides the Agent, some
features need the device's OS:

- `OhrKeys` and `OhrPush` need an OhrTech OS with TEE keys; `OhrKeys.isAvailable()` tells you, and
  otherwise their calls throw `OhrException.Unsupported`.
- The kiosk exit PIN's power menu item and key sequence work once the device's OhrTech OS supports
  them. `OhrKiosk.requestExit()` works with Agent 1061 alone.
- A fleet's response timeout for an app is also the app's "isn't responding" (ANR) time on OhrTech
  OS 2026110901 and later, with Agent 1062.

## R8 and ProGuard

The Kotlin library ships its own consumer rules, which keep the Agent's binder interfaces and the
`OhrTech` JCA provider. R8 applies them to your app by itself: you need no rules of your own. Your
`OhrPushService` subclass is kept because your manifest declares it. The Flutter plugin and the
React Native module bring the library, and its rules, with them; `OhrTech.Device` is trim- and
NativeAOT-safe.
